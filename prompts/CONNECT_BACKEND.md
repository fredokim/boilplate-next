# next 보일러플레이트를 공용 백엔드에 연동

백엔드는 `fredokim/boilplate-server`에 있다. react 보일러플레이트가 이미
연동되어 있고, 이 문서는 next를 같은 서버에 붙이는 작업이다.

아래 단계는 각각 독립적으로 실행 가능한 프롬프트다. 한 번에 하나씩 실행하고,
완료 조건을 만족한 뒤 다음으로 넘어간다.

---

## 배경 — 여기는 다른 저장소들과 상황이 다르다

vue와 react는 mock을 MSW로 가로챈다. **next는 mock 백엔드를 실제로 구현해
갖고 있다.**

`src/app/api/` 아래에 라우트 핸들러가 열 개 넘게 있다.

```
/api/auth/login       /api/dashboard/kpi      /api/users/count
/api/auth/session     /api/dashboard/chart    /api/notifications
/api/health           /api/dashboard/table    /api/audit-logs
```

`src/app/api/auth/login/route.ts`는 이런 모습이다.

```ts
export async function POST() {
  return NextResponse.json(
    createApiSuccess({ accessToken: "mock-access-token", user: dummySession.user }),
  );
}
```

즉 브라우저에서 보면 이미 진짜 HTTP 엔드포인트가 응답하고 있고, 그 안이
더미 데이터일 뿐이다.

두 개의 클라이언트가 있다.

- `src/core/api/clientApiClient.ts` — 브라우저에서 `/api/*`를 `fetch`한다.
- `src/core/api/serverApiClient.ts` — **HTTP를 하지 않는다.** 넘겨받은
  페이로드를 봉투 형식으로 파싱할 뿐이다. 서버 컴포넌트가
  `@/core/mock/dummyData`의 값을 여기에 넣어 쓴다.

**좋은 소식이 하나 있다.** next의 DTO는 이미 서버 계약과 맞는다.
`AuthUserDto`가 `permissions: string[]`을 갖고 로그인 응답이
`{ accessToken, user }`다. vue는 `roles`를 갖고 있어 고쳐야 하지만 여기는
그대로 쓸 수 있다. react에서 옮겨온 코드이기 때문이다.

---

## 핵심 결정 — 라우트 핸들러를 어떻게 할 것인가

두 가지 길이 있고, 이 결정이 이후 단계 전부를 좌우한다.

**(가) 라우트 핸들러를 백엔드로 향하는 프록시로 바꾼다.**

`src/app/api/*/route.ts`가 더미를 돌려주는 대신 백엔드에 요청을 전달한다.
브라우저는 여전히 자기 출처의 `/api/*`만 보므로 쿠키 문제가 그대로 해결되고,
서버 컴포넌트도 같은 백엔드를 서버에서 직접 부를 수 있다. Next를 쓰는 이유에
가장 부합하는 형태이며, 흔히 BFF라고 부른다.

비용은 엔드포인트마다 전달 코드를 써야 한다는 것과, 쿠키·헤더를 양방향으로
정확히 옮겨야 한다는 것이다. 특히 백엔드가 내려주는 `Set-Cookie`를 브라우저
쪽 응답에 그대로 실어야 하고, 브라우저의 쿠키를 백엔드로 실어 보내야 한다.
하나라도 빠지면 로그인은 되는데 갱신이 안 되는 식으로 어긋난다.

**(나) `next.config`의 rewrites로 `/api/*`를 백엔드로 넘긴다.**

전달 코드를 쓰지 않아도 되고 설정 몇 줄로 끝난다. 대신 기존 라우트 핸들러를
전부 지워야 하고(rewrite와 핸들러가 같은 경로에서 충돌한다), 서버 컴포넌트가
백엔드를 부르려면 별도의 서버용 클라이언트가 필요하다.

**권장은 (가)다.** 이 저장소의 존재 이유가 서버 경계를 보여주는 것이고,
라우트 핸들러는 이미 그 경계로 존재한다. 지우는 것보다 실제 서버를 향하게
만드는 편이 이 보일러플레이트가 설명하려는 바에 맞는다.

다만 전부를 한 번에 바꾸지 않는다. 아래는 인증부터 시작해 하나씩 옮기는
순서다.

---

## 이 작업의 범위

포함한다: 백엔드 주소 설정, 인증 경로의 프록시 전환, 서버 컴포넌트용
클라이언트, 남은 엔드포인트 전환, 실시간 트랜스포트, 계약 테스트.

포함하지 않는다: 더미 데이터 제거(mock 모드는 유지한다), 배포.

---

## 단계 4-1 — 백엔드 주소와 모드를 설정으로 뺀다

지시:

1. `BACKEND_URL` 환경변수를 읽는 서버 전용 설정 모듈을 만든다. 값이 없으면
   mock 모드로 동작한다.
2. **이 값은 서버에만 있어야 한다.** `NEXT_PUBLIC_` 접두사를 붙이지 않는다.
   붙이면 백엔드 주소가 브라우저 번들에 들어가고, 브라우저가 백엔드를 직접
   부를 수 있게 되어 단일 출처 전제가 무너진다.
3. `.env.example`에 항목을 적는다.

완료 조건:

- `BACKEND_URL` 없이 `npm run dev`가 지금과 똑같이 동작한다.
- 빌드 산출물에서 백엔드 주소를 검색해 나오지 않는 것을 확인한다.

---

## 단계 4-2 — 인증 세 경로를 프록시로 바꾼다

`login`, `session`, 그리고 아직 없는 `refresh`다.

지시:

1. 백엔드로 요청을 전달하는 헬퍼를 하나 만든다. 엔드포인트마다 복사하지
   않는다.
2. **쿠키를 양방향으로 옮긴다.** 들어온 요청의 `Cookie` 헤더를 백엔드로
   보내고, 백엔드 응답의 `Set-Cookie`를 브라우저 응답에 싣는다. 이것이 이
   단계에서 가장 틀리기 쉬운 부분이다.
3. `/api/auth/refresh` 라우트를 새로 만든다. 지금 없다.
4. `BACKEND_URL`이 없으면 기존 더미 응답을 그대로 돌려준다. 한 파일이 두
   모드를 모두 처리한다.

완료 조건:

- mock 모드에서 로그인이 예전과 똑같이 동작한다.
- 서버 모드에서 로그인 후 브라우저에 refresh 쿠키가 **실제로 저장된 것**을
  개발자 도구에서 확인한다. `Set-Cookie` 전달을 빠뜨리면 여기서 걸린다.
- 새로고침 후에도 세션이 유지된다.

---

## 단계 4-3 — 401 갱신을 배선한다

지시:

1. `clientApiClient`가 401을 받으면 한 번만 갱신하고 한 번만 재시도하게
   한다.
2. **갱신은 단일 비행이어야 한다.** 백엔드의 refresh token은 회전하며, 이미
   사용된 token이 다시 제시되면 재사용으로 판단해 세션 패밀리 전체를
   폐기한다. 화면 로드 시 요청 다섯 개가 동시에 401을 받고 각각 갱신을
   부르면, 첫 번째가 회전시킨 뒤 나머지 넷이 쓴 토큰을 내밀고, 서버는 그것을
   공격으로 읽는다. 병렬 갱신은 사용자를 로그아웃시킨다. react의
   `src/core/api/refreshSingleFlight.ts`가 이 문제를 푼 코드다.
3. 갱신 요청 자체는 재시도 대상에서 제외한다.

완료 조건:

- 동시에 401이 여러 건 나는 화면에서 `/api/auth/refresh` 요청이 **정확히
  한 번** 발생하는 것을 네트워크 패널로 확인한다.

---

## 단계 4-4 — 서버 컴포넌트가 백엔드를 부를 수 있게 한다

지금 `serverApiClient`는 HTTP를 하지 않는다. 넘겨받은 값을 파싱만 한다.

지시:

1. 서버에서 백엔드를 직접 호출하는 함수를 추가한다. 기존 파싱 함수는
   그대로 두고 그 위에 얹는다. mock 모드에서는 예전처럼 더미를 파싱한다.
2. **서버 컴포넌트는 브라우저의 쿠키를 자동으로 갖지 않는다.** 인증이 필요한
   호출이면 `cookies()`에서 읽어 명시적으로 실어 보내야 한다. 이것을
   빠뜨리면 서버 렌더링에서만 401이 나고 클라이언트에서는 멀쩡한, 원인을
   찾기 어려운 상태가 된다.
3. `"server-only"` 표시를 유지한다. 이 코드가 클라이언트 번들에 들어가면
   백엔드 주소가 함께 들어간다.

완료 조건:

- 서버 렌더링되는 화면이 서버 모드에서 실제 데이터를 보여준다.
- 로그아웃 상태로 같은 화면을 열면 인증 오류가 아니라 로그인 화면으로 간다.

---

## 단계 4-5 — 남은 엔드포인트를 옮긴다

`dashboard/*`, `users/count`, `notifications`, `audit-logs`, `health`.

지시:

1. 백엔드에 대응 엔드포인트가 있는 것부터 옮긴다. `contracts/openapi.json`
   또는 백엔드의 스펙을 보고 확인한다.
2. **대응이 없는 것은 옮기지 않는다.** 더미로 남기고, 그 사실을 라우트
   핸들러 주석에 적는다. 존재하지 않는 엔드포인트를 부르는 코드를 조용히
   남기지 않는다.
3. 옮긴 것과 남긴 것의 목록을 문서에 적는다.

완료 조건:

- 서버 모드에서 각 화면을 열어 데이터가 오는지 확인한다.
- 콘솔에 404나 검증 오류가 없다.

---

## 단계 4-6 — 실시간 트랜스포트를 붙인다

지시:

1. `realtime/`에 서버 트랜스포트를 만든다. react의
   `serverChatTransport.ts`와 `serverTopologySource.ts`가 프로토콜의
   본보기다.
2. **WebSocket은 라우트 핸들러로 프록시할 수 없다.** Next의 라우트 핸들러는
   HTTP 업그레이드를 중계하지 못한다. `next.config`의 rewrites는 할 수 있다.
   즉 실시간만은 (나) 방식이 필요하다. 이 예외를 문서에 적는다.
3. 전송은 HTTP, 수신은 소켓이다. 권한·멱등성·rate limit이 HTTP 경로에 있고
   소켓에 다시 구현하면 답이 두 벌 생긴다.
4. 스위치가 실제로 트랜스포트를 고르는지 확인한다. react에서 서버
   트랜스포트를 만들고 단위 테스트까지 했는데 배선 지점이 mock을
   하드코딩하고 있어서, 서버 모드인데 화면에는 "Connected"라고 표시되며
   지어낸 메시지가 흐른 적이 있다.

완료 조건:

- 서버 모드에서 채팅 화면이 데이터베이스에 있는 메시지를 보여준다.
- 브라우저를 열어둔 채 HTTP로 메시지를 보내면 새로고침 없이 도착한다.

---

## 단계 4-7 — 계약 테스트를 추가한다

지시:

1. 백엔드의 `openapi.json`을 `contracts/openapi.json`으로 가져온다.
2. 프론트가 호출하는 URL을 **소스에서 추출해** 스펙과 대조한다. 손으로
   목록을 적지 않는다. react에서 그렇게 했다가 서버가 구현한 적 없는
   엔드포인트를 놓쳤다.
3. 이 저장소에서는 브라우저가 부르는 `/api/*`가 자기 라우트 핸들러다.
   따라서 대조 대상은 **라우트 핸들러가 백엔드로 보내는 경로**다. 이 차이를
   테스트 주석에 적는다.

완료 조건:

- 스펙에서 경로 하나를 지우면 실패하고 되돌리면 통과한다. 두 경우를 모두
  실행해 확인한다.
- `check:ci`에 포함된다.

---

## 단계 4-8 — 문서와 포트폴리오

지시:

1. `DEPLOYMENT.md`를 만든다. 라우트 핸들러가 프록시 역할을 하므로 브라우저는
   단일 출처만 본다는 점, 실시간만 rewrites를 쓴다는 예외를 적는다.
2. README에 서버 모드 실행 방법과 `BACKEND_URL`을 적는다.
3. 포트폴리오를 갱신한다. 현재 "백엔드는 React 저장소에만 있습니다"라고
   적혀 있고, 이 작업이 끝나면 사실과 달라진다.

완료 조건:

- `npm run check:ci`가 통과한다.
- 포트폴리오를 다시 굽고 아티팩트를 갱신한다.
